BUILD, RUN AND TEST
===================
All commands run from the project folder (C:\Users\rkovalenko\Projects\rustCrates).
The binary finds STORAGE\, the tokenizer and the training data through relative paths.

Features
--------
(none)       f32, CPU only (default)
cuda         every complex matmul on the GPU (cuBLAS); CPU fallback if CUDA is not found
dtype-f64    whole crate in f64 (exact equivalence tests; f64 is ~64x slower than f32 on the RTX 3060)


1. Production build
-------------------
// CPU, f32
cargo build --release

// GPU, f32 (recommended for training on the laptop)
cargo build --release --features cuda

// GPU, f64
cargo build --release --features "cuda dtype-f64"

// optional: optimized for this CPU (binary then only runs on CPUs with the same instruction set)
$env:RUSTFLAGS="-C target-cpu=native"; cargo build --release --features cuda

// faster build (no LTO, a few percent slower at runtime), e.g. for short tool runs
cargo build --profile quick --features cuda
-> binary in .\target\quick\

[profile.release]
opt-level = 3  -> for speed, e.g. better performance, more binary files
opt-level = "z" for size, e.g. smaller size

build and run in one go (rebuilds first if the code changed):
cargo run --release --features cuda -- train


2. Run the binary
-----------------
.\target\release\wav-transformer.exe <command>

Windows locks a running .exe, so `cargo build` fails while training runs. To keep working during a
long training, start a copy:
copy target\release\wav-transformer.exe train.exe
.\train.exe train

CUDA: nvcuda.dll and cublas64_12.dll must be on the PATH. At startup the program prints
"CUDA initialized successfully" or "CUDA not available. Falling back to CPU".


3. Training and generation
--------------------------
Two models with the same architecture, each with its own model file:
  RM transformer   (row-major, batched GPU matmuls, weights cached on the GPU)  STORAGE\transformer_rm_v1
  Vec transformer  (reference implementation)                                    STORAGE\transformer_01.04.2025

// train [epochs] [batches|all] [batch_size] [new|resume] [learning_rate]
// default: 100 epochs, all records (1071 training / 119 validation), batch size 16, new model, learning rate 0.0003
.\target\release\wav-transformer.exe train
.\target\release\wav-transformer.exe train 40 all 16 new 0.0003
.\target\release\wav-transformer.exe train 50 all 16 resume          // continue the saved model
.\target\release\wav-transformer.exe train 5 4 2                     // only 4 batches (8 records), quick check
.\target\release\wav-transformer.exe train-vec 40 all 16             // same for the Vec transformer

The records are mixed in a fixed order, so every training holds out the same validation questions; the split of
the last training is saved next to the model (STORAGE\<model>.split.json). In the web UI the Generate card lists
the validation questions (never trained on) and the training questions to try them out against the expected answer.

Training format: the text, then the question on the next line, then <sep> and the answer (no labels).
The input can be typed freely: the question may stand before, inside or after the text (it is moved behind the
text), and JSON escapes pasted from the data file (f\u00fcr) are decoded.

// generate an answer: text and question in any order (asks for the input if none is given)
.\target\release\wav-transformer.exe predict "Die Broncos gewannen den Super Bowl 50. Wer gewann den Super Bowl 50?"
.\target\release\wav-transformer.exe predict-vec

// web UI: choose the model, train (live progress, loss chart, stop) and generate
.\target\release\wav-transformer.exe server      // or without a command; then open http://localhost:7860

// spectral flow (image model), also in the web UI (model "Spectral flow")
// spectral-train [steps] [size] [gray|rgb] [mnist|<image folder>] [new]
// size: 32, 64, 128, 256 or 512; an image folder is searched recursively (PNG, JPEG, BMP, WebP, GIF, TIFF),
// every image is centre-cropped to a square and resized. Without 'new' the saved model is continued and keeps
// its size and colour. Model: STORAGE\spectral_flow\checkpoint.bin
.\target\release\wav-transformer.exe spectral-train 100000                          // MNIST 32x32 grayscale
.\target\release\wav-transformer.exe spectral-train 50000 128 rgb C:\Images\faces new
.\target\release\wav-transformer.exe spectral-sample [ckpt] [out.png] [count] [seed] [steps] [scale]

With --features cuda the large matrix multiplications of the spectral model also run on the GPU (cuBLAS);
large images (256, 512) need it. Images per step default to what fits in memory: 64 (32 px), 32 (64 px),
16 (128 px), 8 (256 px), 4 (512 px).

// is the GPU used? (second terminal: process with type C, GPU-Util > 0 %)
nvidia-smi -l 1


4. Tests
--------
Most layer and equivalence tests only exist with dtype-f64 (they compare at 1e-10).
Use --release: the debug build is much slower.

// all tests, f64 (~4 min)
cargo test --release --features dtype-f64

// all tests, f32 (the dtype-f64-only tests are skipped)
cargo test --release

// RM layers vs normal layers (forward, backward, weight gradients, updates)
cargo test --release --features dtype-f64 rm

// whole RM transformer vs normal transformer (one training step, serialization, learning)
cargo test --release --features dtype-f64 test_transformer_rm -- --nocapture

// same RM tests with the GPU matmul (on a machine with CUDA)
cargo test --release --features "cuda dtype-f64" rm

// GPU matmul tests with timings (skipped when CUDA is not found)
cargo test --release --features cuda test_gpu_matmul -- --nocapture
cargo test --release --features "cuda dtype-f64" test_gpu_matmul -- --nocapture

// one test after the other (shows which test hangs)
cargo test --release --features "cuda dtype-f64" test_gpu_matmul -- --nocapture --test-threads=1

// training data split (1071 training / 119 validation)
cargo test --release test_all_records_split

// run specific test under release version (incl. tests marked #[ignore]):
cargo test --release test_train_transformer -- --nocapture --ignored

cargo test --no-default-features

// test for f64
cargo test --features dtype-f64 -- --nocapture
cargo test --features dtype-f64
